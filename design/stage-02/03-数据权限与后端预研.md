# 数据、权限与后端预研

2026-10-19。供设计评审使用，非最终数据库设计、非生产安全保证；此阶段不部署，不锁定供应商。正式需求确认后再定义字段、迁移、接口与验收。

## 1. 两条候选路线

| 维度 | React + TypeScript + Supabase / PostgreSQL | React + TypeScript + 独立 API / PostgreSQL |
|---|---|---|
| 适合场景 | 团队较小、希望复用托管认证与数据库能力 | 学校已有统一认证、校内网络/托管要求、业务审批复杂 |
| 权限实现 | 数据库 grants + RLS，敏感管理操作走受控服务 | API 的动作/字段/范围授权，数据库低权限角色与 RLS 防御 |
| 优点 | 减少基础服务搭建工作；身份与数据库可衔接 | 易对接现有学校系统和定制审批，服务边界集中 |
| 需承担 | 正确配置 RLS、存储权限、服务端密钥及复杂事务 | 认证集成、部署运维、限流、媒体存储、备份恢复等 |
| 共同限制 | 浏览器不能保存服务端密钥；不能只靠路由守卫或隐藏按钮授权 | 同左 |

预研结论：先保持前端数据接口中立。确认学校认证、部署与网络条件、维护人员和数据存储要求后再选。Supabase 可作为候选，不把它当成自动解决所有隐私问题的服务。其 Auth 提供身份能力；访问哪些业务数据仍须独立授权。[Supabase Auth](https://supabase.com/docs/guides/auth)

## 2. 概念数据模型

| 模型 | 关键字段与关系 | 约束与用途 |
|---|---|---|
| Users | id、auth_subject、status | 认证系统映射；业务表不存明文密码 |
| MemberProfiles | user_id、display_name、avatar_asset_id、bio、joined_at、position | user_id 唯一；本人可写字段白名单；组织字段受控 |
| Teams | id、kind、name、parent_id | kind 区分届别/分队/部门，不把届别和分队混成单值 |
| TeamMemberships | member_id、team_id、valid_from/to | 多对多及历史有效期，避免转队覆盖历史 |
| Applications | id、contact_reference、status、reviewer、timestamps | 申请人可无账号；最少材料；单独状态查询凭据，不在日志记录凭据 |
| ActivationInvites | application_id、token_hash、expires_at、consumed_at | 一次使用；只存令牌摘要；绑定目标身份 |
| Courses | id、category、title、version、status、review_status、audience | 五类课程；发布必须经过获资质人员审核 |
| Lessons | course_version_id、id、order、content、asset_id、completion_rule | 顺序唯一；内容引用审核版本，更新课程不改写旧完成历史 |
| CourseEnrollments | member_id、course_version_id、status | 选课/分配；结合成员状态决定访问 |
| LearningProgress | member_id、lesson_id、course_version_id、status、position、completed_at | 唯一键防重复完成；进度从有效必修章节导出，不随意写总百分比 |
| TrainingSessions | id、project、team_scope、start/end、status | 场次与参加人分开，时间长度可验证 |
| TrainingRecords | member_id、session_id、attendance、duration、source | 每人每场次唯一；区分出勤、请假、缺勤、不适用 |
| AssessmentStandards | id、project、version、unit、range、effective_date | 分/秒/次/米各自标准；可比性需显式判断 |
| Assessments | member_id、session_id、standard_id、raw_value、status、revision | 缺考不等于零；草稿/发布分开；更正保留历史 |
| Milestones | member_id、type、date、source_type/id、visibility | 来自实际记录或经确认人工登记，不凭算法推断晋升 |
| Honors | member_id/team_id、title、date、evidence、publication_consent | 仅真实材料；个人荣誉公开需授权 |
| GrowthReflections | owner_id、content、sharing_grant、updated_at | 默认私密；与心理记录不同；分享指定且可撤回 |
| Content | type、slug、body、audience、review_status、published_at | 简介、活动、公告、公开人物、相册；与私人表分离 |
| MediaAssets | owner、storage_key、kind、audience、review、consent、alt_text | 公开与私有存储分区；教材需审核；访问受控 |
| Roles / Permissions | role_id、permission_key | 按具体操作定义，避免一个 admin 标记获得所有数据 |
| UserRoleGrants / ScopeGrants | user_id、role_id、resource_scope、expires_at | 用户可有多职责，范围与期限可撤销 |
| AuditEvents | actor、action、object_ref、outcome、time、request_id | 记录管理操作；不记录密码、令牌、敏感日记正文 |

私人域单独规划：PrivateJournals（owner_id、加密正文、版本、删除时间）；SupportResources 与 SupportChannels 属于可审核发布的资源域，不包含个人求助信息。默认不建立站内求助记录表；将来确需向专业人员发送信息时，另行设计逐次明确同意、指定接收方、用途和保存期限。

## 3. 成长数据的口径

训练次数与时长来自已发布的有效 TrainingRecords，不从前端卡片值反推。出勤率展示公式与请假处理规则。课程进度来自课程版本中的必修章节；不同版本分开，迁移规则显式批准。考核曲线按项目+标准版本+单位分组，同一时点多次记录须说明采用最近一次、最佳值或全部记录，不悄悄取最高分。

Assessments 的草稿不进入成长页；发布后成员能查看原始结果、单位、标准和登记时间。更正记录需原因与前后版本，统计只采用当前有效已发布版本，保留审计。

## 4. 服务端权限与隐私边界

身份先验证，再核对成员资格、具体 permission、scope 和字段白名单。正式用户不能通过把请求中的 member_id 改成他人来读取/改写记录。列表、搜索、导出、聚合、文件 URL 同样受控。服务端批量更新在一次事务内检查所有目标，不能只检查首个成员。

Supabase 暴露给客户端的表要同时检查 grants 与 RLS；服务端高权限凭据不得进入浏览器。将成员本人访问与教学范围策略分别定义，并分别验证读、建、改、删。[Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)

PostgreSQL 表所有者通常可绕过行级策略，超级用户和 BYPASSRLS 角色也可绕过；因此“页面没有入口”或“已开 RLS”不能被宣传为运维人员在技术上绝对无法读取。[PostgreSQL 行安全](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

心理记录放独立私有域、独立 API 与窄权限数据库身份；不继承管理员的业务读取权、不暴露通用搜索/导出。正式上线前选择并验证加密与密钥托管模式，明确有权解密者、恢复方式与运维风险。如果要求连服务运维都不可读，需要另行评估端到端加密及无法恢复密钥的代价，不在本阶段空口保证。普通管理员只维护公开支持资源与真实渠道。

心理页面不接入记录正文的分析、会话回放或第三方埋点；不把访问心理专区当成能力指标。运营审计只保留必要操作元数据，不能通过标题/标签泄露敏感内容。共享设备退出时清除私有缓存；不在通用 service worker 中缓存私密内容。

## 5. 账号、媒体、备份与运维

认证优先评估学校 SSO 或成熟托管认证，不自行发明密码存储。独立密码认证需由成熟组件处理强散列与重置流程；高权限账号启用二次验证/多因素认证。服务端校验会话、有效期与撤销，安全 cookie 场景防 CSRF，限制登录和申请滥用，防止账号枚举。

公开媒体与内部教材分桶/路径授权；内部资源使用短效访问凭证或受控下载，不能凭永久公开链接绕过课程权限。上传限制类型/大小、检查内容、处理元数据及肖像授权；课程视频另备字幕/文字稿。

数据库备份与照片/视频对象分别规划。Supabase 数据库备份不包括 Storage API 中实际对象，不能把数据库恢复等同于媒体恢复。[Supabase 备份说明](https://supabase.com/docs/guides/platform/backups)

正式上线前确定恢复点/恢复时间目标、加密与密钥备份、保留期限、删除和恢复后的数据一致性、异地副本与恢复演练。访问和管理审计限制保留范围；离队、账号停用与撤销授权应有实际生效流程。

## 6. 待设计确认后的实施顺序

1. 确定首页与六页视觉、移动端行为、申请条件、组织结构、考核标准、真实教材和渠道。
2. 完成明确标示的前端演示：四条路径、非敏感本地持久化、错误和空态、键盘操作；不收真实密码或私人日记。
3. 选择后端与部署方案；实现账号、邀请激活、成员资格、角色范围、审计和权限拒绝测试。
4. 接公开内容及成员资料；跑通申请审核、访问隔离与最小字段编辑。
5. 接课程版本、审核、资源授权与学习进度；完成幂等与跨设备验证。
6. 接训练场次、出勤、标准、考核发布/更正及成长投影，验证事务与并发冲突。
7. 私人日记在独立隐私评审、加密/恢复/删除策略明确后单独接入；资源阅读和真实渠道可先上线。
8. 备份恢复、限流、审计、撤权与跨角色越权验证通过后，再按小范围试运行推进正式上线。

尚待组织提供：真实届别和分队、谁可审核招募、课程专业审核人、训练统计口径、联系方式、校方认证/部署约束、资料保留周期。上述未知项不阻碍当前视觉设计，不自动假定为官方制度。
